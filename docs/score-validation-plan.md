# 점수 기준 검증·조정 기능 계획 (초안)

작성 2026-11-13. 아직 코드·DB는 바꾸지 않았다. 사용자가 확인한 뒤 단계별로 진행한다.

## 왜 하나

4·5차 페르소나 평가에서 남은 요청 1위다(12명). 묶으면 다섯 가지다.

| 요청 | 페르소나 |
| --- | --- |
| 관리자가 위험 기준을 화면에서 조정하고, 바꾼 기록과 근거를 남기고, 바뀌면 팀에 알리기 | 9, 36, 48, 49 |
| '잘못 울린 알림'을 따로 표시하기 | 50 |
| 기록이 빠진 날(기기·동기화 문제)과 안 한 날을 구분하기 | 57 |
| 적중률 같은 성능 지표, 기간별 이탈률 | 15, 59 |
| 회복 사례 모아 보기, 요약과 수치가 다를 때 표시, 근거·출처, 검증 연구 지원 | 11, 18, 22, 29 |

지금 기준(`src/lib/risk.ts`의 `RISK_CONFIG`)은 처방 기준을 바탕으로 정한 **초기 가정치**다. 이 기능은 기준을
"검증된 것"으로 만드는 게 아니라, **실제 데이터가 쌓였을 때 사람이 기준을 점검하고 고칠 수 있게 하는 도구**다.
화면에서도 그렇게 말한다. 데이터가 가상 환자 8명뿐이라 지금 나오는 지표는 의미가 없다는 안내를 계속 둔다.

## 나누어 진행 (각 단계가 따로 배포 가능)

### 1단계: '잘못 울린 알림' 결과 (작음)

- **DB (SQL 011a)**
  - `alerts_outcome_check`에 `'잘못 울림'`을 추가한다.
  - `set_contact_outcome`(009)은 그대로 둔다. 상담원은 지금처럼 미정·연락 불가만 기록한다.
  - 판단은 의료진만 한다.
- **코드**
  - `alert-outcome.ts`의 `ALERT_OUTCOMES`와 통계(`outcomeStats`)에 '잘못 울림'을 넣는다. 단계별 회복 비율 옆에 '잘못 울림 비율'을 둔다.
  - `AlertOutcome.tsx`에 버튼을 추가하고, 결과 메모에 이유를 적도록 안내한다.
  - CSV 내보내기에도 들어간다(값만 늘어남).
- **테스트**: `alert-outcome.test.ts`에 통계 경우를 추가한다.
- **실행 순서**: SQL 먼저, 그다음 배포. 순서가 바뀌면 그사이 '잘못 울림' 저장이 실패한다.

### 2단계: 기록 누락 표시 (중간)

- **DB (SQL 011b)**: 새 테이블 `play_log_gaps(id, patient_id, start_date, end_date, reason '기기 문제'|'동기화 누락'|'기타', note, created_by, created_at)`
  - RLS 읽기: 담당자와 관리자
  - RLS 쓰기: 의사·간호사·관리자
  - 상담원: 보호자 통화에서 알게 되는 경우가 많으므로 쓰기를 허용할지 정해야 한다(아래 결정할 것).
- **risk.ts**
  - `computeRisk(patient, logs, asOf, opts?)`에 `missingDays`(날짜 목록)를 받는다.
  - 그날은 연속 미접속일과 회차 지연에서 빼고, 이유에 "기록 누락 N일 제외"를 넣는다.
  - 계산은 계속 `risk.ts` 한 곳에서만 한다. 부르는 곳(`queries.ts`, `daily-check-run.ts`, `counselor-view.server.ts`, `calendar.ts`, 시뮬레이터)은 값만 넘긴다.
- **화면**
  - 환자 상세 캘린더에서 날짜를 골라 '기록 누락으로 표시'를 누른다.
  - 캘린더에는 빗금으로 표시하고, 연락 이력에 남긴다.
- **주의**
  - 누락으로 표시하면 점수가 내려가므로, 누가 언제 왜 표시했는지 꼭 남긴다.
  - 매일 점검의 알림 판단도 같은 값을 쓴다.

### 3단계: 기준 조정과 변경 기록 (큼)

- **DB (SQL 011c)**: 새 테이블 `risk_config_versions(id, config jsonb, note, created_by, created_at, active boolean)`
  - 활성 버전은 하나만 둔다(부분 고유 인덱스).
  - RLS 읽기: 로그인한 의료진 전체. 쓰기: 관리자만(함수 `activate_risk_config(config, note)`로 새 버전을 만들고 활성화).
  - 처음 버전은 지금 `RISK_CONFIG` 값을 그대로 넣는다.
  - `risk_scores`·`alerts`에 `config_version_id`를 추가해, 어떤 기준으로 계산했는지 남긴다.
- **risk.ts**
  - `RISK_CONFIG`는 기본값으로 남긴다.
  - `computeRisk`가 `config`를 받아 쓰고, 없으면 기본값을 쓴다.
  - `validateRiskConfig`(순수 함수, 테스트)로 구간이 겹치지 않는지, 0~100을 빈틈없이 덮는지, 계수가 음수가 아닌지 확인한다.
- **불러오기**
  - 화면: `riskConfigQuery` 하나로 읽어 모든 계산에 넘긴다.
  - 서버(Cron·상담원 화면): 같은 테이블을 읽는다.
  - 테이블이 없거나 읽기에 실패하면 기본값을 쓴다.
- **화면 (설정 → 정보 '위험 점수 기준'을 관리자에게는 편집 가능하게)**
  - 단계 구간, 계수, 치료이탈 연속 미접속 일수를 고친다.
  - **바꾸기 전 미리보기**: 지금 환자들에게 새 기준을 적용하면 단계가 어떻게 바뀌는지 보여 준다(몇 명이 올라가고 내려가는지). 시뮬레이터처럼 저장하지 않는다.
  - 저장할 때 **바꾼 이유를 꼭 적는다**.
  - 변경 기록 목록을 두고, 예전 버전으로 되돌릴 수 있게 한다(되돌리기도 새 버전으로 남김).
  - 기준이 바뀌면 대시보드 위에 "위험 기준이 바뀌었습니다(날짜, 바꾼 사람, 이유)" 안내를 7일 동안 띄운다(페르소나 49).
- **주의**
  - 기준을 바꾸면 그날 매일 점검에서 점수가 크게 바뀌어 알림이 몰릴 수 있다. 저장 화면에 "새 기준 첫 점검에서 알림 N건 예상"을 보여 준다.
  - 기준 변경 다음 날 점검은 '단계 변화'만 알리고 '15점 상승' 조건은 쉬게 할지 결정이 필요하다.
  - 지금 브라우저에 저장하는 '연락할 환자 기준 점수'(설정 → 업무)는 개인 화면 설정이라 이 기능과 별개로 둔다.

### 4단계: 성능 지표와 회복 사례 (중간, DB 변경 없음)

- 설정 → 데이터에 '기준 점검' 화면을 두고, 관리자와 의료진이 본다.
  - **알림 결과 분포**: 기준 버전별, 단계별로 회복·이탈·연락 불가·잘못 울림 비율.
  - **놓친 이탈**: 알림 없이 치료이탈이 된 환자 수. risk_scores 기록으로 계산한다.
  - **처방 주차별 이탈률**: 1~4주차 중 어디서 많이 그만두는지.
  - **회복 사례 목록**: 결과가 '회복'인 알림. 무엇을 했는지(연락 기록 메모)와 함께 보여 준다.
- "적중률"이라는 말은 쓰지 않는다. 결과를 기록한 알림만 세므로 표본이 치우친다. "결과를 기록한 알림 중 비율"로 쓰고, 표본 수를 항상 함께 보여 준다.
- 계산은 `src/lib/score-check.ts`(순수 함수와 테스트)에 둔다. 위험 점수 계산은 하지 않고 저장된 값만 센다.

## 순서와 크기

| 단계 | DB | 크기 | 먼저 필요한 것 |
| --- | --- | --- | --- |
| 1 잘못 울림 | 제약 조건 수정 | 작음 | 없음 |
| 2 기록 누락 | 새 테이블 1개 | 중간 | 없음 |
| 3 기준 조정 | 새 테이블 1개, 컬럼 2개 | 큼 | 없음(2단계와 같은 `computeRisk` 인자 정리를 함께 씀) |
| 4 지표·사례 | 없음 | 중간 | 1단계(잘못 울림), 3단계가 있으면 버전별로 나눔 |

추천 순서는 1 → 4 → 2 → 3이다. 1·4는 작고 바로 쓸모가 있고, 3은 위험이 가장 크다(점수가 한꺼번에 바뀜).

## 확인 방법

- 순수 함수 테스트: 통계, 누락일 반영, 기준 검증, 지표.
- 권한 시험 SQL(`003_staff_rls_test.sql`)에 항목을 추가한다.
  - 상담원은 기준 변경과 '잘못 울림' 기록이 막힘
  - 관리자가 아니면 기준 변경이 막힘
  - 누락 표시 권한
- 배포 사이트 화면 확인은 사용자가 한다(로그인 필요).

## 결정할 것 (사용자)

1. 진행 순서: 추천(1 → 4 → 2 → 3)대로 할지.
2. 상담원이 '기록 누락'을 표시할 수 있게 할지. 보호자 통화에서 "기기가 고장 났다"를 가장 먼저 듣는 사람이 상담원일 수 있다.
3. 기준을 바꿀 수 있는 사람: 관리자만으로 할지, '의사 + 관리자'로 할지.
4. 기준 변경 다음 날 '15점 상승' 알림을 쉬게 할지.
5. 화면에서 "적중률" 대신 쓸 말(제안: "결과를 기록한 알림 중 회복 비율").

## 하지 않는 것

- 기준을 자동으로 고치는 기능(데이터로 기준을 추천·적용). 사람이 판단하고, 앱은 근거를 보여 주기만 한다.
- 지표를 "검증 결과"처럼 표현하기.
- 실제 환자 데이터 사용(지금은 가상 환자뿐).
